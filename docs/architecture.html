How a machine gets assembled

There are two different graphs in this repo, and confusing them is what makes the configs hard to grok. Loading is flat: every file under modules/ is slurped in as an equal. Selection is layered: hosts pick system profiles, and system profiles drag in home profiles. This page lets you walk the second graph one host at a time.

Graph one · loading (flat, automatic)

Every file is a peer — nothing imports anything

flake.nix

Declares inputs, then makes exactly one call: mkFlake (import-tree ./modules).

import-tree scans

Every .nix under modules/ loads — features, hosts, options alike. Paths containing /_ are skipped.

Files fill profiles

Each file merges settings into named profiles: darwin.*, nixos.*, home.* (declared in core/options.nix).

Hosts select

A host file lists which profiles it wants and hands them to darwinSystem / nixosSystem.

Outputs appear

Ordinary darwinConfigurations.* and nixosConfigurations.* — what just switch builds.

Consequence: a file's location never matters and no file is "imported by" another. Only the profile names inside it matter.

Graph two · selection (layered, explicit)

Three vocabularies, one rule

darwin.*

macOS system layer (nix-darwin): system packages, Homebrew, launchd, fonts. Selected by Mac host files.

nixos.*

Linux system layer: boot, services, desktop, gaming. Selected by hxtn's host file.

home.*

Your user layer (home-manager): dotfiles, per-user packages. Never selected by hosts directly.

The one rule: hosts only ever select system profiles. Each system profile can import reusable home.* profiles into home-manager.users.thomashexton or define tightly scoped user settings there directly. darwin.base brings Aerospace to both Macs; darwin.personal imports home.personal and adds the Mac-only Zsh and streamrip settings.

Practical

"Where do I put…?"

  1. A new app/tool → one new file in modules/. Inside it, assign to the profile(s) matching who should get it: every machine → *.base; dev machines → *.workstation; personal life → *.personal; work → home.professional. Put personal Mac-only user settings below darwin.personal.home-manager.users.thomashexton.
  2. System-level vs user-level? Binary on PATH for everyone → darwin.*/nixos.* environment.systemPackages. Reusable dotfiles or per-user packages → the matching home.*; settings specific to one system profile → its nested home-manager.users configuration.
  3. Give an existing feature to another machine → usually nothing to edit in the feature; change which profile it assigns to, or add the profile to the host's select-list.
  4. A whole new capability class (like gaming was) → declare the profile in core/options.nix, wire its home.* import in core/darwin.nix or core/nixos.nix, then select it from a host.
  5. Machine-specific one-offs (hostname, boot, hardware) → the literal block at the bottom of that host's file. Nowhere else.
Fine print
  • modules/**/_*.nix is invisible to import-tree — only hosts/hxtn/_hardware-configuration.nix uses this, imported explicitly by hxtn.nix.
  • Profiles also pull from flake inputs: darwin.base ← Determinate + home-manager modules; nixos.base ← home-manager; nixos.gaming ← nix-citizen; nixos.hyprland ← a pinned Hyprland (see README for the removal criteria).
  • core/options.nix declares the three profile namespaces, every permitted profile name, and flake.darwinConfigurations; unknown profile names are errors. formatter.nix is plain flake-parts perSystem. Neither is a feature.
